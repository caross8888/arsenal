# 설계: 성인 커리어 브라우저 진행 + 랭킹 등록 때 한 번 검증

작성 2026-10-22 · 상태: 설계 확정(미구현, Codex 구현 예정) · 대체: `chunked-seasons-design.md`(4시즌 묶음, 폐기) · 선행 작업: `local-reroll-handoff.md`(유스 로컬 리롤, 구현됨)

## 1. 목표

성인 커리어(19세~은퇴)도 유스처럼 브라우저에서 계산한다. 서버는 **랭킹 등록 때 한 번**, 18세 확정 상태와 성인 선택 기록으로 은퇴까지 재계산해 검증한다.

| | 지금 | 이 설계 |
|---|---|---|
| 커리어 한 판 서버 요청 | 약 38번(성인 시즌당 2번 남짓) | 2번(18세 확정 1 + 등록 1) |
| 값 조작 | 불가(서버 계산) | 불가(등록 때 서버 재계산) |
| KV(진행) | 0 | 0 |
| 미래 미리 보기 | 불가 | 가능(§6 — 감수) |
| 서버 CPU(요청 1번) | 약 1.6ms | 등록 때 평균 약 47ms, 최대 약 103ms(§8) |

### 4시즌 묶음 설계를 버린 이유(사용자와 논의 2026-10-22)

- 묶음으로 나눈 주된 이유는 무료 플랜 CPU 10ms였다. 커리어 전체 재계산(평균 47ms)이 한도를 넘는다고 봤다.
- 운영 관찰 가능성 로그 실측: 10/20 오후~10/22 오후 커리어 요청 **32,457건이 전부 `outcome: ok`**, `cpuTimeMs` 최대 **111ms**, 시간대별 최대 20~67ms. Cloudflare는 10ms를 넘는 실행을 끊지 않고 통과시키고 있다. 커리어 전체 재계산(최대 약 103ms)은 이미 운영에서 문제없이 도는 범위다.
- 묶음 설계도 진행 상태는 브라우저에 두고, 새로고침 리롤과 묶음 넘어 미리 보기를 막지 않았다(옛 문서 §6). 공정성 차이가 거의 없는데 요청이 3배 많고 구현(묶음 경계·묶음 시드·`a=chunk`·`a=state`)이 무겁다.
- 시드를 감추는 건 실익이 작다. 시드로 결과를 미리 계산하려면 게임 코드를 따로 돌려야 하고, 즐기는 사람은 그렇게까지 하지 않는다(킥루 저장값을 직접 고쳐 보고 확인). 반드시 막을 건 **값 조작**이고, 그건 서버 재계산이 막는다.

## 2. 지금 구조 요약(바꾸지 않을 것)

- 계산은 `public/career/sim-v{1,2}/`를 서버(`api/career.js`)와 브라우저가 같이 쓴다. `Math.random`·`Date.now`·`crypto`가 없어 결정적이다.
- 난수는 `mulberry(eventSeed(C) ^ hashStr('사건키|나이'))`처럼 **사건마다 따로** 만든다(`career-mode.md` "난수 사용처 분류"). 그래서 선택 기록만으로 재계산 검증이 성립한다.
- `eventSeed(C) = C.seed2 ?? C.seed`(`sim-v1/seeds.js`). 유스는 `seed`, 18세 확정(`a=commit`) 뒤 미래 사건은 `seed2`.
- 유스 로컬 기록: `careerToken`에 `career-local-v2:{version,seed,input,choices}`. 확정 때 서버가 처음부터 재생(`local.js`의 `replay`)한다.
- 성인은 지금 암호화 토큰(`career-token-v1`, deflate)으로 시즌 행동마다 서버를 부른다: `season`·`penalty`·`military`·`scout`·`service-return`·`next`·`retire`. **이 경로는 진행 중인 옛 커리어용으로 그대로 둔다**(§3.4).

## 3. 핵심 설계

### 3.1 시뮬레이션 규칙은 그대로, 수학 함수만 결정적으로(sim-v3)

성인 진행은 지금도 `seed2` 하나로 계산한다. 이 설계는 **같은 `seed2`, 같은 `flow.step`을 브라우저에서 돌릴 뿐**이라 밸런스·확률·사건은 v2와 같다. 다만 브라우저 엔진과 무관하게 같은 값이 나오도록 수학 함수와 정렬을 바꿔야 해서(§3.6) 결과가 아주 드물게 달라질 수 있다. 그래서 **sim-v3**로 낸다.

- `public/career/sim-v3/`는 v2를 복사하되 §3.6의 교체만 한다. 데이터·병역·국제대회·PK처럼 v1을 공유하던 모듈 중 §3.6의 함수를 쓰는 것(`international.js`·`finance.js`·`wages.js`·`club_final.js`·`penalty-rules.js` 등)은 v3용으로 갈라야 한다 — 공유 파일을 그 자리에서 고치면 v1/v2 결과가 바뀐다.
- 밸런스는 바꾸지 않는다. §9의 2번 테스트로 v2와 v3의 결과가 (경계에 걸린 드문 경우를 빼고) 같은지 확인한다.

### 3.2 `seed2`를 결정적으로

지금 `a=commit`은 `seed2`를 무작위(`crypto.randomBytes`)로 만든다. 브라우저가 `seed2`를 알게 되면, 같은 유스 기록으로 확정을 반복해 좋은 `seed2`가 나올 때까지 고를 수 있다(미래 전체를 계산할 수 있으므로). 이 손쉬운 경로만 막는다.

- `seed2 = HMAC-SHA256(CAREER_SEED_SECRET, stableJSON(유스 기록 + next))`의 앞 4바이트(부호 없는 32비트).
- `C.id`도 같은 방식으로 결정적으로 만든다(`'id|'` 접두사로 구분, 앞 8바이트 hex). 같은 유스 기록을 다시 확정하면 같은 커리어가 되므로 `career:done:{id}`의 중복 등록 방지가 그대로 성립한다.
- 남는 경로: 유스 선택이나 유스 시드를 바꿔 확정하면 다른 `seed2`가 나온다. 이건 유스 로컬 리롤(이미 허용)과 같은 수준이라 감수한다(§6).
- `CAREER_SEED_SECRET`은 Cloudflare 대시보드 "비밀"로 둔다(CLAUDE.md 백엔드 기준 8). 토큰 암호화 키와 섞지 않는다.

### 3.3 상태는 누가 들고 있나

- **서버**: 18세 확정 상태(`seed2`·`id` 포함)를 지금과 같은 암호화 토큰(`career-token-v1`)으로 봉인해 브라우저에 맡긴다. KV에 커리어 상태를 저장하지 않는다.
- **브라우저**: 확정 토큰(열 수 없음) + 확정 시점 평문 상태 + 성인 선택 기록을 저장한다. 진행 중 상태는 평문 상태에서 선택 기록을 재생해 만든다(새로고침해도 같은 결과).
- 확정 응답에 평문 상태와 `seed2`를 같이 준다. 브라우저가 그걸로 계산을 시작한다.

### 3.4 새 커리어만

- 새로 시작하는 커리어만 이 방식(저장 형식 `career-local-v3`)으로 진행한다.
- 진행 중인 v1/v2 서버 토큰 커리어는 끝날 때까지 지금처럼 시즌마다 서버로 진행한다. 옛 `career-local-v2` 유스 기록도 지금 `commit` 경로를 유지한다.

### 3.5 버전 고정(로컬 진행 중 배포 대비)

지금은 시즌마다 서버가 계산해 코드가 바뀌어도 어긋날 일이 없다. 로컬 진행은 다르다 — 누군가 성인 커리어를 진행하는 도중에 계산 규칙을 바꿔 배포하면, 브라우저가 계산한 결과와 등록 때 서버가 새 코드로 재계산한 결과가 달라져 정직한 판이 §4.2의 점수 대조에 걸린다.

- 커리어는 확정 때의 시뮬레이션 버전(`C.simVersion`, 이 설계로 시작하는 커리어는 3)으로 끝까지 계산한다. 확정 토큰과 브라우저 기록 양쪽에 버전을 남긴다.
- **계산 결과가 달라지는 변경(밸런스·확률·사건 추가)은 반드시 새 버전 폴더**(`sim-v4/`…)로 낸다. 서버는 옛 버전을 지우지 않고 커리어의 버전대로 재계산한다(지금 `sim-v1`·`sim-v2`를 둘 다 두는 것과 같은 방식).
- 결과가 안 바뀌는 수정(문구·화면·`view`의 표시 필드)은 버전을 안 올려도 된다. 애매하면 §9의 2번 테스트(같은 기록 재생 결과 비교)를 돌려 확인한다.
- 브라우저는 페이지를 새로 받을 때 최신 코드를 받으므로, 진행 중 커리어의 버전 폴더도 화면이 계속 불러올 수 있어야 한다(`public/career/sim-v{N}/`를 지우지 않는다).

### 3.6 브라우저 엔진 차이(결정성)

같은 코드·같은 시드·같은 선택이면 결과가 같아야 등록 대조(§4.2)가 정직한 판을 통과시킨다. 덧셈·곱셈·나눗셈·`Math.sqrt`는 IEEE 754로 모든 엔진에서 같지만, 아래는 엔진마다 마지막 자리가 다를 수 있다. 서버(Cloudflare, V8)와 아이폰 사파리(JavaScriptCore)가 다르게 계산하면, 그 값이 확률 경계에 걸린 판에서 판정이 갈리고 정직한 아이폰 사용자가 불일치로 거부된다.

- **초월 함수**: `Math.exp`·`Math.log`·`Math.pow`·`**`(소수 지수)·`Math.sin`·`Math.cos`·`Math.atan2`·`Math.hypot`·`Math.cbrt`. 표준이 정확한 반올림을 요구하지 않는다. 2026-10-22 기준 시뮬레이션 공용 코드(`sim-v1/sim.js`·`international.js`·`finance.js`·`club_final.js`·`wages.js`, `sim-v2/sim.js`, `penalty-rules.js`)에 `Math.exp` 18곳, `Math.hypot` 15곳, `Math.sin` 12곳, `**` 11곳, `Math.pow` 8곳 등이 있다. `match-playback.js`는 화면 재생 전용이면 대상이 아니다(판정에 쓰이는지 확인할 것).
- **`localeCompare`**: 기기 언어 설정(ICU)에 따라 순서가 달라질 수 있다. 시뮬레이션 정렬 3곳(`windows.sort(... a.id.localeCompare(b.id))`).

v3에서 할 것:
1. 판정·누적에 쓰이는 초월 함수를 `sim-v3/detmath.js`의 결정적 구현으로 바꾼다. 방법은 둘 중 하나:
   - 직접 구현(정수·사칙연산만 쓰는 다항식 근사). 정확도는 게임에 충분한 수준이면 된다.
   - 또는 결과를 고정 자리로 반올림(`Math.round(x * 1e9) / 1e9`)한 뒤 쓰기. 마지막 자리 차이를 지우지만, 반올림 경계에 걸리면 여전히 갈릴 수 있어 1번이 더 확실하다.
   - 정수 지수 거듭제곱(`x**2`)은 곱셈으로 바꾼다.
2. `localeCompare`는 `a < b ? -1 : a > b ? 1 : 0`으로 바꾼다.
3. 다시 들어오지 않게: `scripts/test_career_determinism.mjs`가 `sim-v3/` 아래에서 위 함수 사용을 찾아 실패시킨다(`detmath.js` 제외).

### 3.7 숨김 값

지금 성인 단계는 숨은 재능·구단 명성 숫자·발롱 점수 등을 응답에 넣지 않는다(`career.js` 머리말). 브라우저가 계산하면 평문 상태에 이 값들이 들어 있어 개발자 도구로 보인다. 유스 로컬에서 이미 같은 수준이고 조작은 서버 재계산으로 막히므로 **감수한다**. 화면에는 지금처럼 표시하지 않는다.

## 4. API

### 4.1 확정(`a=commit`) — 18세 → 성인

```
POST ?a=commit {version:3, seed, input, choices, next}
→ {token, seed2, state, ...view}
  token : 18세 확정 상태 봉인(이후 등록 때 그대로 돌려보낸다)
  seed2 : §3.2의 결정적 시드
  state : 확정 직후 평문 상태(next 적용 후) — 브라우저 계산의 시작점
```

처리는 지금 `commit`과 같다(`replay` → `validateNext` → `seed2`·`id` 넣기 → `step(C,'next',next)`). 다른 점은 `seed2`·`id`가 결정적이고, 평문 상태를 같이 준다는 것뿐이다.

### 4.2 등록(`a=submit`) — 재계산 포함

```
POST ?a=submit {token, choices:[{a, ...입력}], claim:{score, digest}} + Authorization: Bearer <승부예측 토큰>
  token   : 4.1에서 받은 확정 토큰
  choices : 성인에서 실제로 한 행동 순서대로(season·injury·penalty·military·scout·service-return·next·retire)
  claim   : 브라우저가 계산한 은퇴 결과 — 점수와 은퇴 상태 요약 해시(`stateDigest`, 서버·브라우저 공용 함수)
→ 지금 submit 응답과 같음 {registered, rank, best, improved, key}
```

서버 처리:
1. 로그인 확인 → 확정 토큰을 연다. v3 확정 상태인지 확인한다.
2. `choices`를 하나씩 검증(§5.2)하며 `flow.step`으로 재생한다. 재생 중엔 `view`·`prefetch`를 계산하지 않는다(CPU 절약).
3. 재생 결과가 은퇴(`phase==='retired'`)가 아니면 거부한다. 은퇴 뒤 남은 기록이 있어도 거부한다.
4. **점수 대조**: 재계산한 점수·`stateDigest`가 `claim`과 다르면 **등록하지 않는다**(409, `{error:'기록이 서버 계산과 달라요', mismatch:true}`).
   - 버전을 고정하면(§3.5) 정직한 판은 항상 같으므로, 다르면 저장값 조작이나 버그다. 서버가 계산한 진짜 점수로 조용히 등록하지 않는다(사용자 지정 — 조작해도 아무 일 없이 등록되면 조작 신호가 남지 않는다).
   - 원인 추적용으로 관찰 가능성 로그에 한 줄 남긴다: `{careerMismatch:1, id, simVersion, claimed, actual, choices:길이, engine}`. 선택 기록 원문·닉네임·전체 User-Agent는 남기지 않는다. `engine`은 `safari`/`chrome`/`firefox`/`other` 네 값만 남긴다(사용자 확인 2026-10-22).
5. 이후는 지금 `submit`과 같다(`career:done:{id}` NX → 월 등록 수 → 랭킹 반영). 은퇴 카드(`cardView`)는 서버가 재계산한 상태로 만든다(브라우저가 보낸 카드는 믿지 않는다).
6. 재생 실패(검증 오류)는 400, 그 밖의 오류는 지금처럼.

화면: 400·409(불일치)면 등록 버튼 자리에 이유를 보여 주고 다시 시도하게 하지 않는다(같은 기록은 몇 번을 보내도 같다). 커리어 기록은 지우지 않는다.

등록하지 않는 판은 서버를 다시 부르지 않는다. 은퇴 화면·카드는 브라우저가 같은 `cardView`로 그린다.

### 4.3 CPU 초과 대비

- 응답이 오류(Cloudflare 1102·503 등)면 화면은 기록을 지우지 않고 "잠시 후 다시 등록" 버튼을 보여 준다. 같은 기록 재제출은 결정적이라 같은 결과가 나온다.
- 관찰 가능성 로그에서 `a=submit`의 `outcome`이 `exceededCpu`/`exceededResources`로 반복되면 그때 묶음 검증(옛 `chunked-seasons-design.md`)으로 바꾼다. 처음부터 넣지 않는다.

## 5. 브라우저

### 5.1 저장 형식

`careerToken` = `career-local-v3:` + JSON
```
유스:   {version:3, stage:'youth', seed, input, choices}         // 지금 v2와 같은 모양
성인:   {version:3, stage:'adult', token, seed2, state, choices}
```
- 크기: 확정 시점 상태 수 KB + 성인 선택 기록(시즌당 수십 바이트). localStorage 한도 안이다. 지금 `MAX_BYTES=24000`은 유스 기록 상한이라 성인 기록은 따로 둔다(예: 120KB).
- 아이폰 사파리는 7일 동안 방문이 없으면 사이트 저장소를 지울 수 있다(ITP). 그러면 진행 중 커리어를 잃는다. 지금 유스 로컬·옛 묶음 설계도 같은 조건이라 새로 생기는 문제는 아니다. 안내 문구는 두지 않는다(옛 설계에서 사용자 지정).

### 5.2 행동 검증 넓히기(서버·브라우저 공용, `local.js`)

지금 `validateAction`은 유스 행동(`season`·`next`·`scout`·`penalty`)만 안다. 성인에서 추가로:
- `military`: `action`이 `apply`/`regular`이고 `militaryView(C)`가 허용할 때.
- `service-return`: 복무 복귀 단계일 때.
- `retire`: `C.phase==='result'`이고 은퇴 가능(`forced` 또는 나이 조건)일 때.
- `penalty`: `x`·`y`·`power` 범위(`penalty-rules.js`와 같은 범위).
- 대표팀 경기 결정(`decisions`), 승부차기 키(`key`) 등 지금 서버가 받는 입력 전부를 화이트리스트로 검증한다. 구현 전에 `flow.step`이 읽는 `body` 필드를 전수 조사할 것.
- 기록 길이 상한: 성인 행동 수에 상한을 둔다(예: 시즌 수 상한 × 시즌당 최대 행동 수). 무한 기록으로 CPU를 태우는 요청을 막는다.

### 5.3 화면 흐름

- `crLocal*`(유스 로컬 실행기)을 성인까지 넓힌다. 시즌 진행·결과·부상·승부차기·병역·은퇴는 `flow.step`/`view`를 브라우저에서 부른다.
- 성인 진행 중 서버 요청 0. 승부차기 그림·대표팀 경기 재생도 지금처럼 브라우저.
- 은퇴 → 브라우저가 은퇴 화면·카드를 그림 → "랭킹 등록"을 누르면 `a=submit` 한 번.

## 6. 공정성(미리 보기·리롤)

### 6.1 막는 것

- **값 조작**: 서버가 확정 토큰(봉인)과 선택 기록만으로 재계산한다. 브라우저 상태·카드는 믿지 않는다. 조작한 판은 브라우저 점수가 재계산과 달라 등록이 거부된다(§4.2의 4).
- **같은 유스로 확정 반복해 시드 고르기**: `seed2`가 유스 기록의 HMAC이라 같다(§3.2).
- **같은 커리어 두 번 등록**: `career:done:{id}`(지금 그대로).

### 6.2 막지 않는 것(감수 — 사용자 지정)

- **미래 미리 보기**: 브라우저가 `seed2`를 알아서, 코드를 따로 돌리면 은퇴까지의 결과를 선택별로 계산할 수 있다. 하는 사람이 극소수이고 막으려면 서버 진행(지금 방식)으로 돌아가야 한다.
- **새로고침 리롤**: 저장값을 되돌려 다른 선택을 고를 수 있다. 옛 묶음 설계·지금 유스 로컬도 같다.
- **유스를 바꿔 다른 `seed2` 받기**: 유스 로컬 리롤과 같은 수준.

## 8. CPU

- 이 작업 환경 Node 실측(커리어 35개): 커리어 전체 재계산 평균 약 47ms, 최대 약 103ms. 등록 재계산은 성인 부분만이라 이보다 조금 적다.
- 운영 실측(위 §1): 커리어 요청 32,457건 전부 ok, 최대 111ms.
- 줄이는 수단: 재생 중 `view`·`prefetch`·카드 계산 생략(카드는 마지막에 한 번), 토큰 열기·봉인 1회씩.
- 배포 뒤 `a=submit`의 `cpuTimeMs` 분포와 `outcome`을 확인한다(§4.3).

## 9. 테스트(필수)

`WHOAMI_SECRET='test-only-secret'`, `env -u KV_REST_API_URL`로(기존 테스트와 같은 방식).
1. **브라우저 = 서버**: 시드 수천 개 × 무작위 선택으로 성인 전체를 로컬 실행기로 진행하고, 등록 재계산 결과(점수·카드)와 같은지 대조(`scripts/test_career_local_adult.mjs`).
2. **v2 = v3(밸런스 유지)**: 같은 유스·같은 `seed2`·같은 선택을 아래 세 분류로 집계하고 각 판 수·비율을 PR에 적는다(사용자 확인 2026-10-22).
   - 완전 동일: 카드·상태가 정확히 같음(버전 식별자 차이 제외).
   - 표시값만 다름: 점수·능력치·사건 목록·판정은 전부 같고 `chance` 같은 소수 값만 다르며 소수 6자리 반올림 기준으로 같음.
   - 실질 차이: 점수·능력치·사건·판정 중 하나라도 다름. 시드와 처음 갈린 사건(나이·사건 키·v2 값/v3 값)을 함께 적는다. **1%를 넘으면 진행하지 말고 먼저 사용자에게 알린다.**
   - v3 브라우저·서버 비교에는 이 허용 범위를 적용하지 않는다. 표시값까지 완전 일치해야 한다.
3. **점수 대조**: 브라우저 상태의 잠재력·능력치를 고친 뒤 진행한 판은 409(불일치)로 거부되고 랭킹에 안 들어간다. 정직한 판은 통과.
4. **버전 고정**: v3로 시작한 로컬 커리어를, 결과가 다른 가짜 v4 규칙이 추가된 서버에 등록해도 v3로 재계산돼 통과.
5. **엔진 차이**(사용자 확인 2026-10-22 — 아이폰 실기기 대신 아래로 검증):
   - 같은 시드·선택 기록 수백 개를 Playwright WebKit(JavaScriptCore)에서 은퇴까지 돌리고 `stateDigest`가 서버(Node/V8)와 전부 같은지 자동 대조한다. 환경에서 실행할 수 없으면 실행 불가 사유와 대신 실행할 명령을 PR에 적는다.
   - 같은 검증을 수행하는 브라우저 페이지를 제공한다. 사용자가 PC 크롬·엣지·파이어폭스에서 실행해 결과를 전달할 수 있어야 한다.
   - `test_career_determinism.mjs`의 금지 함수 검사는 반드시 통과해야 한다.
   - 등록 불일치 로그에는 엔진 종류(`safari`/`chrome`/`firefox`/`other`)만 추가하고 전체 User-Agent는 남기지 않는다.
6. **거부**: 은퇴로 안 끝난 기록, 은퇴 뒤 남은 기록, 화이트리스트 밖 입력, 길이 상한 초과, 다른 커리어 토큰이 전부 400.
7. **결정성**: 같은 유스 기록의 확정은 항상 같은 `seed2`·`id`. 같은 기록 재등록은 409(이미 등록).
8. **기존 커리어 무변화**: `test_career_legacy_reroll.mjs`(v1 서버 토큰 24개), v2 로컬 기록 재생 테스트가 그대로 통과.
9. 기존 `scripts/test_career_*.mjs` 전부.
10. 실제 크롬(모바일 390px): 성인 진행 중 API 0회, 은퇴 후 등록 1회, 새로고침 후 이어 하기, 등록 실패 시 기록 유지·재시도.

## 10. 배포 순서

1. 서버: `a=commit`(v3)·`a=submit`(재계산), `CAREER_SEED_SECRET` 비밀 등록. 화면은 그대로(v2로 새 커리어 시작) → v3 경로가 안 쓰이는 상태로 먼저 배포.
2. 운영에서 테스트 커리어로 v3 확정·등록 확인, `a=submit`의 CPU 로그 확인.
3. 화면: 새 커리어를 v3로 시작. 진행 중인 v1/v2 커리어는 끝날 때까지 지금 방식.
4. `CLAUDE.md`·`career-mode.md`에 구조와 요청 수를 적는다.

## 11. 정한 것(사용자 확인 2026-10-22)

- 4시즌 묶음 대신 **등록 때 한 번 검증**.
- 시드는 감추지 않는다. 미래 미리 보기·새로고침 리롤은 감수한다(§6.2).
- CPU 초과가 운영에서 반복될 때만 묶음 검증으로 바꾼다(§4.3).
- 커리어는 시작 버전으로 끝까지 계산한다. 결과가 바뀌는 변경은 새 버전 폴더로 낸다(§3.5).
- 등록 때 브라우저 점수와 서버 재계산이 다르면 **거부**한다(진짜 점수로 대신 등록하지 않음, §4.2).
- 엔진마다 다를 수 있는 수학 함수·`localeCompare`를 결정적 구현으로 바꾼 **sim-v3**로 새 커리어를 시작한다(§3.6).
- 구현은 Codex가 맡는다. 이 문서와 `local-reroll-handoff.md`를 함께 넘긴다.
