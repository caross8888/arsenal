# 설계: 성인 커리어 4시즌 묶음 진행 (브라우저 계산 + 묶음마다 서버 검증)

> **폐기(2026-10-22)** — `local-adult-design.md`(등록 때 한 번 검증)로 대체. 운영 로그에서 CPU 10ms 초과 실행이 끊기지 않는 게 확인돼(커리어 요청 32,457건 전부 ok, 최대 111ms) 묶음으로 나눌 이유가 없어졌다. 등록 검증이 운영에서 CPU 초과로 반복 실패할 때의 대안으로만 남긴다.

작성 2026-10-21 · 상태: 폐기(대안으로 보관) · 선행 작업: `local-reroll-handoff.md`(유스 로컬 리롤, 구현됨)

## 1. 목표

성인 커리어(19세~은퇴)의 시즌 진행을 브라우저에서 계산하고, 서버는 **4시즌마다 한 번** 선택 기록을 재계산해 확정한다.

| | 지금 | 묶음 진행 |
|---|---|---|
| 커리어 한 판 서버 요청 | 약 38번(성인 시즌당 2번 남짓) | 약 6~7번 |
| 값 조작 | 불가(서버 계산) | 불가(서버 재계산) |
| KV(진행) | 0 | 0 |
| 미래 미리 보기 | 불가 | 진행 중인 묶음 안(최대 4시즌)만 |
| 서버 CPU(요청 1번) | 약 1.6ms | 약 9ms 평균, 최대 약 20ms(실측 환산, §8) |

킥루(kickru.com)처럼 전부 로컬로 돌리고 검증하지 않는 방식은 쓰지 않는다. 우리 랭킹은 누적이라 조작·미리 보기로 만든 기록이 계속 남는다(사용자와 논의 2026-10-21).

## 2. 지금 구조 요약(바꾸지 않을 것)

- 계산은 `public/career/sim-v{1,2}/`를 서버(`api/career.js`)와 브라우저가 같이 쓴다. `Math.random`·`Date.now`·`crypto`가 없어 결정적이다.
- 난수는 `mulberry(eventSeed(C) ^ hashStr('사건키|나이'))`처럼 **사건마다 따로** 만든다(`docs/career-mode/career-mode.md` "난수 사용처 분류"). 한 선택이 무관한 다른 사건을 흔들지 않아서 재계산 검증이 성립한다.
- `eventSeed(C) = C.seed2 ?? C.seed`(`sim-v1/seeds.js`). 유스는 원래 `seed`, 18세 확정(`a=commit`) 뒤 미래 사건은 서버 난수 `seed2`.
- 유스 로컬 기록: `careerToken`에 `career-local-v2:{version,seed,input,choices}`. 확정 때 서버가 처음부터 재생(`local.js`의 `replay`)한다.
- 성인은 암호화 토큰(`career-token-v1`, deflate)으로 시즌 행동마다 서버를 부른다: `season`·`penalty`·`military`·`scout`·`service-return`·`next`·`retire`.

## 3. 핵심 설계

### 3.1 묶음과 시드

- **묶음 경계**: 18세 결과(지금 `commit` 지점), 22·26·30·34·38세 결과 화면(`phase==='result'`, `age%4===2`). 은퇴(`phase==='retired'`)는 묶음 중간에도 묶음을 끝낸다.
- **묶음 시드**: 묶음 k(0부터, 19~22세가 k=0)마다 서버가 정한다.
  `seed2_k = HMAC-SHA256(CAREER_CHUNK_SECRET, C.id + '|' + k)`의 앞 4바이트(부호 없는 32비트).
  - 무작위가 아니라 **결정적**이다. 같은 묶음을 다시 제출해도 다음 묶음 시드가 바뀌지 않으므로, 제출을 반복해 시드를 리롤할 수 없다(§6).
  - 경계에서 서버가 `C.seed2 = seed2_k`로 바꾼 뒤 경계의 `next`를 적용한다. 지금 `commit`이 `seed2`를 넣고 `next`를 적용하는 순서와 같다.
  - 브라우저는 **진행 중인 묶음의 시드만** 안다. 다음 묶음 시드는 경계를 제출해야 받는다.
- `CAREER_CHUNK_SECRET`은 Cloudflare 대시보드 "비밀"로 둔다(CLAUDE.md 백엔드 기준 8). 토큰 암호화 키(`KV_REST_API_TOKEN`에서 파생)와 섞지 않는다.

### 3.2 시뮬레이션 버전

시드가 묶음마다 바뀌면 같은 선택이라도 지금(`seed2` 하나)과 결과가 달라진다. 그래서 **sim-v3**로 올린다.

- `public/career/sim-v3/`는 v2처럼 `sim.js`·`flow.js`·`local.js`만 새로 두고 나머지(데이터·병역·국제대회·PK)는 v1을 공유한다. 계산 규칙 자체는 v2와 같고, 달라지는 건 seed2 교체 시점뿐이다.
- 상태에 `C.simVersion = 3`, `C.chunk = k`(지금 묶음 번호).
- **기존 커리어는 그대로**: v1/v2 서버 토큰은 지금처럼 시즌마다 서버로 진행한다. 옛 v2 로컬 유스 기록(`career-local-v2:`)도 지금 `commit`(v2) 경로를 유지한다. 새로 시작하는 커리어만 v3.

### 3.3 상태는 누가 들고 있나

- **서버**: 묶음 시작 상태(시드 포함)를 지금과 같은 암호화 토큰으로 봉인해 브라우저에 맡긴다. 서버는 KV에 커리어 상태를 저장하지 않는다.
- **브라우저**: 묶음 시작 토큰(열 수 없음) + 자기가 계산한 평문 상태 + 묶음 안의 선택 기록을 저장한다.
  - 평문 상태는 서버가 보내지 않는다. 브라우저가 직접 계산한 값이고(18세 2KB → 34세 약 44KB, 실측), 서버는 같은 계산 결과의 해시만 돌려줘 맞는지 확인한다(§4.2).
  - 해시가 다르면(코드 버전 차이·버그) 브라우저는 `a=state`로 서버 평문 상태를 한 번 받아 갈아끼운다.

### 3.4 숨김 값

지금 성인 단계는 숨은 재능·구단 명성 숫자·발롱 점수 등을 응답에 넣지 않는다(`career.js` 머리말). 브라우저가 계산하면 평문 상태에 이 값들이 들어 있어 개발자 도구로 보인다. 유스 로컬에서 이미 같은 수준이고 조작은 서버 재계산으로 막히므로 **감수한다**. 화면에는 지금처럼 표시하지 않는다.

## 4. API

### 4.1 확정(`a=commit`) — 18세 → 첫 묶음

v3 유스 기록이면 지금 `commit`과 같되 `seed2` 대신 `seed2_0`을 넣고 다음을 돌려준다.

```
POST ?a=commit {version:3, seed, input, choices, next}
→ {token, chunk:0, seed2, stateHash, ...view}
```

### 4.2 묶음 확정(`a=chunk`) — 신규

```
POST ?a=chunk {token, choices:[{a, ...입력}], next?}
  token   : 이 묶음 시작 때 받은 암호화 토큰
  choices : 이 묶음에서 실제로 한 행동 순서대로(season·injury·penalty·military·scout·service-return·next·retire)
  next    : 경계(22·26…세 결과)의 다음 시즌 선택({pick, trait}). 은퇴로 끝난 묶음은 없음
→ 경계:  {token, chunk:k+1, seed2:seed2_{k+1}, stateHash, ...view}
→ 은퇴:  {token(retired), stateHash, ...view}   // 이후 a=submit은 지금 그대로
```

서버 처리:
1. 토큰을 연다. `simVersion===3`, `phase`가 묶음 시작 상태인지 확인한다.
2. `choices`를 하나씩 검증하고 `flow.step`으로 재생한다. 검증은 `local.js`의 `validateAction`을 성인 행동까지 넓힌 것(§5.2).
3. 재생 결과가 경계(`age%4===2 && phase==='result'`) 또는 은퇴가 아니면 거부한다. 묶음을 넘어 진행한 기록도 거부한다.
4. 경계면 `next` 검증 → `C.chunk=k+1`, `C.seed2=seed2_{k+1}` → `step(C,'next',next)` → 봉인.
5. `stateHash = SHA-256(정규화한 평문 상태)`의 앞 16자. 정규화는 서버·브라우저 같은 함수(`sim-v3/local.js`의 `stateDigest`).
6. KV는 쓰지 않는다(§6.2 — 한 번만 쓰기 기록을 두지 않는다).

### 4.3 평문 상태(`a=state`) — 신규, 드문 경우

해시가 안 맞을 때만 브라우저가 부른다. `{token}` → `{state}`. 시드 필드(`seed2`)는 이미 아는 값이라 그대로 보낸다.

### 4.4 이어 하기·기기 변경

로컬 기록이 없는데 토큰만 있으면(다른 기기, 저장소 삭제) `a=state`로 평문 상태를 받아 그 묶음 처음부터 다시 진행한다. 묶음 안에서 하던 진행은 잃는다(최대 4시즌). 지금은 시즌마다 서버 토큰이라 잃는 게 없으니, 별도 안내 문구는 두지 않는다(사용자 지정).

## 5. 브라우저

### 5.1 저장 형식

`careerToken` = `career-local-v3:` + JSON
```
유스:   {version:3, stage:'youth', seed, input, choices}           // 지금 v2와 같은 모양
성인:   {version:3, stage:'adult', token, chunk, seed2, stateHash, state, choices}
```
- `state`는 묶음 시작 평문 상태. 진행 중 상태는 `state`에서 `choices`를 재생해 만든다(새로고침해도 같은 결과).
- 크기: 34세 상태 약 44KB + 선택 기록. localStorage 한도(보통 5MB) 안이다. 지금 `MAX_BYTES=24000`은 유스 기록 상한이라 성인 기록은 따로 둔다(예: 120KB).

### 5.2 행동 검증 넓히기(서버·브라우저 공용, `sim-v3/local.js`)

지금 `validateAction`은 유스 행동(`season`·`next`·`scout`·`penalty`)만 안다. 성인에서 추가로:
- `military`: `action`이 `apply`/`regular`이고 `militaryView(C)`가 허용할 때.
- `service-return`: 복무 복귀 단계일 때.
- `retire`: `C.phase==='result'`이고 은퇴 가능(`forced` 또는 나이 조건)일 때.
- `next`: 묶음 경계가 아닐 때만(경계의 `next`는 `a=chunk`의 `next` 필드로).
- `penalty`: `x`·`y`·`power` 범위(`penalty-rules.js`와 같은 범위).
- 대표팀 경기 결정(`decisions`), 승부차기 키(`key`) 등 지금 서버가 받는 입력 전부를 목록으로 정리해 화이트리스트로 검증한다. 구현 전에 `flow.step`이 읽는 `body` 필드를 전수 조사할 것.

### 5.3 화면 흐름

- `crLocal*`(유스 로컬 실행기)을 성인까지 넓힌다. 시즌 진행·결과·부상·승부차기·병역은 지금처럼 `flow.step`/`view`를 브라우저에서 부른다.
- 경계 결과 화면에서 "다음 시즌" → `a=chunk` 한 번. 실패하면 기록을 그대로 두고 재시도.
- 은퇴 → `a=chunk`(은퇴로 끝) → 랭킹 등록 `a=submit`(지금 그대로).
- 묶음 진행 중 요청 0. 승부차기 그림·대표팀 경기 재생도 지금처럼 브라우저.

## 6. 공정성(미리 보기·리롤)

### 6.1 남는 것

- 진행 중인 묶음의 시드는 브라우저에 있으므로, 코드를 돌려 묶음 안(최대 4시즌) 결과를 미리 보거나 저장값을 되돌려 다시 고를 수 있다. 묶음 크기가 이 범위를 정한다.

### 6.2 막는 것

- **값 조작**: 서버가 묶음 시작 상태(봉인)와 선택만으로 재계산한다. 브라우저 상태는 믿지 않는다.
- **다음 묶음 시드 리롤**: 시드가 `HMAC(id|k)`라 다시 제출해도 같다.
- **묶음 넘어 미리 보기(분기 탐색)는 막지 않는다**(사용자 지정 — KV 사용을 늘리지 않는다). 같은 묶음 토큰을 다른 선택으로 여러 번 제출하면 그다음 묶음들까지 탐색할 수 있다.
  - 지금 서버 토큰 방식도 옛 토큰을 다시 보내면 똑같이 할 수 있어(seed2 고정) 새로 생기는 구멍이 아니다.
  - 막으려면 묶음 확정을 한 번만 받는 기록이 필요한데(`SET career:chunk:{id}:{k} NX`, 커리어당 약 5회) KV가 늘어서 넣지 않았다. 가장자리 캐시(무료)는 데이터센터별·언제든 지워져 확실하지 않고, Durable Objects는 과하다.
  - 같은 선택 재제출(네트워크 재시도)은 결정적이라 같은 결과가 나온다.

## 7. 요청·KV 수(커리어 한 판, 평균 20.8시즌 기준)

| 구간 | 요청 | KV |
|---|---|---|
| 유스 15~18세 | 0 | 0 |
| 18세 확정 | 1 | 0 |
| 성인 묶음 확정 | 약 4~5 | 0 |
| 랭킹 등록 | 1 | 지금과 같음(약 10) |
| 해시 불일치·기기 변경 | 드물게 1 | 0 |

## 8. CPU(무료 플랜 10ms)

실측(이 작업 환경 Node, 커리어 35개): 커리어 전체 재계산 평균 약 47ms, 최대 약 103ms → 4시즌 환산 평균 약 9ms, 최대 약 20ms. 지금 운영 중인 `a=commit`이 4시즌(15~18세) 재생이라 같은 수준이다.

- **구현 전**: 관찰 가능성 로그에서 `a=commit`의 `cpuTimeMs`·`outcome`을 확인한다. `exceededCpu`가 잦으면 묶음을 3시즌으로 줄인다(`age%3` 경계로 바꾸면 된다 — 시드·검증 구조는 같다).
- 줄이는 수단: 재생 중 `view`·`prefetch` 계산 생략(지금 로컬은 `prefetch:false`), 묶음 시작 토큰 열기 1회·봉인 1회만.

## 9. 테스트(필수)

`WHOAMI_SECRET='test-only-secret'`, `env -u KV_REST_API_URL`로(기존 테스트와 같은 방식).
1. **브라우저 = 서버**: 시드 수천 개 × 무작위 선택으로 성인 전체를 로컬 실행기로 진행하고, 묶음마다 `a=chunk` 재계산 결과(상태 해시)와 같은지 대조(`scripts/test_career_chunks.mjs`).
2. **거부**: 묶음을 넘은 기록, 경계가 아닌 곳에서 끝난 기록, 화이트리스트 밖 입력, 다른 커리어 토큰이 전부 400.
3. **재시도**: 같은 묶음 같은 선택 재제출은 같은 응답.
4. **시드**: `seed2_k`가 묶음마다 다르고, 같은 `(id,k)`면 항상 같음. 묶음 k 안의 사건이 `seed2_k`만 쓰는지(이전 묶음 시드로 미래를 계산하는 곳이 없는지) — 예: 계약 연수·병역 일정처럼 여러 해를 미리 정하는 값은 정한 시점의 시드로 고정되는지.
5. **기존 커리어 무변화**: `test_career_legacy_reroll.mjs`(v1 서버 토큰 24개), v2 로컬 기록 재생 테스트가 그대로 통과.
6. 기존 `scripts/test_career_*.mjs` 전부.
7. 실제 크롬(모바일 390px): 성인 묶음 진행 중 API 0회, 경계 1회, 새로고침 후 이어 하기, 해시 불일치 시 `a=state` 복구.

## 10. 배포 순서

1. 서버: `sim-v3`, `a=commit`(v3), `a=chunk`, `a=state`, `CAREER_CHUNK_SECRET` 비밀 등록. 화면은 그대로(v2로 새 커리어 시작) → 운영에서 v3 경로가 안 쓰이는 상태로 먼저 배포.
2. 운영에서 `a=chunk`를 테스트 커리어로 확인, CPU 로그 확인.
